# Architecture

DuckGeneSnap is a static, same-origin browser application. A DuckDB-Wasm worker loads
pinned DuckHTS and Parquet extensions. JavaScript handles file selection and
small chip-text parsing; annotation, VCF/BCF reading, allele keys, reference
sequence lookup, liftover, filtering and export queries run in DuckDB SQL.
The large shipped Parquet bundles remain generated by `scripts/build_assets.R`.

## Build and runtime

1. `npm ci && npm run vendor` builds the DuckDB browser module and copies its
   Wasm binaries/workers into ignored `vendor/`.
2. `npm run stage` downloads DuckHTS signed community 1.5.2 and DuckDB Parquet
   1.5.4 Wasm binaries, verifying the committed SHA-256 manifests.
3. `npm run stage:dev` verifies the unsigned DuckHTS build from the pinned
   public CI artifact (requires `gh`), or accepts an archived `gh run download`
   directory as an argument. Select it with `?duckhts=dev`. Signed community
   1.5.2 cannot read browser `blob:` uploads; the default runtime refuses
   VCF/BCF input rather than silently re-fetching or misparsing it.
4. `npm run serve` serves the checkout with Range support. Staged libraries,
   assets, workers and uploaded file reads stay on the page's origin. No
   genotype file is sent to an application server.

The unsigned artifact is an interim development dependency. When `duckhts@dev`
is published on npm, replace the pinned artifact staging and loader with that
package's exports. Never load an extension from an unpinned CDN at runtime.

## Modules

- `src/db.js`: `openDatabase`, `loadAssets`, `quote`, `rows`.
- `src/ingest.js`: `readChip`, `readVariants`, `detectKind`.
- `src/match.js`: `matchLoci`, `resultQuery`, `pageMatches`.
- `src/export.js`: `exportMatches`.
- `src/convert.js`: `convertChip` uses DuckHTS `fasta_nuc` with an explicit
  uploaded index to determine the REF base for single-base chip calls.
- `src/liftover.js`: `liftVariants` uses `bcftools_liftover` and
  `duckhts_bcftools_norm` to export lifted VCF, TSV or Parquet.
- `src/local-files.js` and root `files-worker.js`: short-lived indexed FASTA
  and chain bridge for DuckHTS readers that require adjacent `.fai` paths.
- `src/app.js`: DOM wiring, validation feedback, page and download controls.

Reference and chain uploads used for liftover are written temporarily to the
browser's Cache Storage, served by a same-origin Service Worker with byte ranges,
and deleted after the operation. This makes local-disk quota, temporary
persistence after abnormal tab termination, and Service Worker availability
operational constraints; browser site-data clearing removes stranded files.
Large genome FASTAs require sufficient local storage. Chip conversion uses
`blob:` readers and does not stage its FASTA in Cache Storage.

## Matching

Every query starts with `(build, chrom_norm, pos)`. For VCF/BCF the source
`REF/ALT` is lifted when necessary, then `variantkey(chrom,pos,ref,alt)` is
computed. An annotation with registered keys requires an exact key; a locus
without keys remains a locus-only hit. Chip text cannot establish REF/ALT and
uses locus matching plus seeded normalized-genotype interpretations. These
are exploratory annotations, not clinical findings. No rsID is used as a
join key.

Results live in `analysis_matches`. Paged queries and exports apply the same
SQL filters. TSV/CSV/Parquet and liftover exports are generated by `COPY` from
browser DuckDB. The page has no style or remote enrichment dependencies.
